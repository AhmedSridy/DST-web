# منظومة DST لإدارة ومراقبة صرف الأسمدة الزراعية

تطبيق ويب عربي كامل من اليمين إلى اليسار (**RTL**) لإدارة ومراقبة صرف الأسمدة الزراعية اليومي (يوريا، نترات، سلفات) وتتبع الجرارات والبوليصات والاعتمادات المتدرجة وقراءة صور الكشوف الورقية بالذكاء الاصطناعي مع دعم العمل دون إنترنت (PWA + Firestore Persistent Cache + IndexedDB).

---

## المبادئ المحاسبية والأمنية الأساسية

- **ترتيب أصناف الأسمدة الثابت**: `يوريا` ← `نترات` ← `سلفات`.
- **المعادلات المعتمدة (دون عمود «الوارد»)**:
  - `المنصرف = بداية اليوم − نهاية اليوم`
  - `فرق التسوية = المنصرف − التسوية`
  - `فرق الشحنة (الجرارات) = العدد الفعلي − عدد البوليصة`
- **حفظ يومي منفصل**: تُحفظ بيانات كل يوم منفصلة لكل `(محافظة + تاريخ)` ولا تُستبدل بيانات الأيام السابقة.
- **المصادقة والصلاحيات**: تسجيل الدخول في الإنتاج يتم عبر **حساب Google فقط** مع دعوات مسبقة من مدير النظام (`user_invites`) وقاعدة صريحة لمدير النظام التأسيسي، مع تطبيق الصلاحيات عبر `firestore.rules`.

---

## الأدوار الوظيفية (RBAC)

| الدور | الصلاحيات الأساسية |
| --- | --- |
| `field_staff` (موظف ميداني) | إدخال كشوف الصرف اليومي والجرارات (بحالة `pending`)، استخدام قراءة الصور بالذكاء الاصطناعي، تقديم التقرير للمراجعة ضمن محافظاته المسموحة. |
| `supervisor` (مشرف محافظة) | كل صلاحيات الموظف الميداني + إدارة الجمعيات (إضافة/تعديل/إيقاف) + مراجعة التقارير وتحويلها لمرحلة المراجعة + اعتماد أو إزالة الجرارات غير المعتمدة نهائيًا ضمن محافظاته. |
| `chief` (رئيس قطاع) | مراجعة واعتماد أو رفض التقارير اليومية (مع حظر الاعتماد الذاتي للتقارير التي أنشأها بنفسه وشرط سبب الرفض)، والإرسال المركزي عبر نقطة النهاية الحقيقية عند تهيئة رابط HTTPS. |
| `admin` (مدير النظام) | إدارة المستخدمين والدعوات والصلاحيات، إعدادات المنظومة والربط المركزي، الحذف النهائي للجمعيات، تنظيف الحقول القديمة، سجل التدقيق الكامل، والإشراف على كل المحافظات. |
| `viewer` (مراقب) | قراءة التقارير والأرصدة والمؤشرات ضمن نطاق محافظاته دون تعديل. |

## التشغيل والتطوير المحلي

### المتطلبات
- Node.js 22+
- npm 10+ (ملف `.npmrc` يفعّل `legacy-peer-deps=true` لتوافق `typescript@^7` مع `@firebase/eslint-plugin-security-rules`)
- Java 21 (لتشغيل اختبارات قواعد أمان Firestore عبر المحاكي المحلي)

### الأوامر
```bash
# تثبيت الحزم
npm install

# تثبيت نظيف في بيئة CI
npm ci

# تشغيل بيئة التطوير (Express + Vite على المنفذ 3000)
npm run dev

# فحص الأنواع (TypeScript)
npm run lint

# تشغيل اختبارات الوحدة
npm test

# فحص قواعد أمان Firestore
npx eslint firestore.rules

# تشغيل اختبارات قواعد أمان Firestore بالمحاكي (يتطلب Java 21)
npm run test:rules

# بناء نسخة الإنتاج
npm run build

# تشغيل الإنتاج (أو تلقائيًا على Cloud Run عند وجود K_SERVICE)
NODE_ENV=production npm start
```

> **ملاحظة حول `start`**: يعتمد أمر `npm start` على `node server.ts` (مدعوم في بيئة التشغيل الحالية Node.js 22+ مع TypeScript strip-types وبيئة النشر). كما يعمل الخادم تلقائيًا بوضع الإنتاج عند توفر `NODE_ENV=production` أو `K_SERVICE`.

## متغيرات البيئة (`.env`)

راجع ملف `.env.example`:

- `GEMINI_API_KEY`: مفتاح Gemini API (سري على الخادم فقط — لا يُكشف للعميل).
- `APP_URL`: رابط النشر العام للتطبيق.

### متغيرات اختيارية (ليست شرطًا للتشغيل أو النشر)
تُعطَّل الميزة المرتبطة بأي متغير اختياري بهدوء عند غيابه ويستمر التطبيق في العمل بصورة طبيعية:

- `GEMINI_API_KEYS` و/أو `GEMINI_API_KEY_2` حتى `GEMINI_API_KEY_10`: مفاتيح Gemini API احتياطية اختيارية على الخادم فقط (مفصولة بفواصل أو أسطر جديدة في `GEMINI_API_KEYS`). عند تجاوز حد الحصة (`429 / RESOURCE_EXHAUSTED`) للمفتاح الحالي، ينتقل الخادم تلقائيًا وبشفافية للمفتاح التالي مع فترة تهدئة مؤقتة (`65` ثانية) للمفتاح المستنفد دون إظهار أي خطأ للمستخدم ما دام هناك مفتاح متاح.
- `GEMINI_OCR_MODEL`: اسم نموذج Gemini لقراءة الكشوف والبوليصات (اختياري؛ الافتراضي `gemini-4-hydrogen` مع مستوى تفكير عالٍ `ThinkingLevel.HIGH` لأعلى دقة متاحة على المفتاح المجاني).
- `VITE_RECAPTCHA_SITE_KEY`: مفتاح reCAPTCHA v3 لتفعيل **Firebase App Check** على العميل وتمرير `X-Firebase-AppCheck` إلى الخادم وFirestore REST (اختياري؛ يُتخطى بأمان إن لم يُضبط).
- `CENTRAL_API_TOKEN`: رمز Bearer اختياري على الخادم فقط يُرسل في ترويسة `Authorization` عند طلبات `POST /api/central/sync`. عند غيابه يُعطّل إرسال التوكن بهدوء دون التأثير على تشغيل التطبيق، ولا يُسجَّل في السجلات ولا يُكشف للواجهة.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`: متغيرات اختيارية تمامًا لإرسال تنبيهات المخزون بالبريد من الخادم لمدير النظام فقط. عند غياب أي منها تُعطَّل ميزة الإرسال التلقائي للبريد بهدوء ويستمر التطبيق في العمل دون طلب أي متغير بيئة.

## نشر قواعد أمان Firestore واختبارها

1. تحقق من سلامة القواعد قبل النشر:
   ```bash
   npx eslint firestore.rules
   ```
2. انشر القواعد من Firebase CLI أو لوحة Firebase Console (`Firestore Database -> Rules`):
   ```bash
   firebase deploy --only firestore:rules
   ```
3. لتشغيل اختبارات قواعد الأمان (`tests/firestore.rules.test.ts`) باستخدام محاكي Firestore (يتطلب Java 21 و`firebase-tools`):
   ```bash
   npm run test:rules
   ```

## القيود المعروفة والملاحظات التشغيلية

1. **تحذير حول تفعيل Firebase App Check (وضع Enforce)**: يقوم العميل بتمرير رمز `X-Firebase-AppCheck` إلى الخادم ويُعيد الخادم تمريره إلى طلبات Firestore REST؛ ومع ذلك **لا يُنصح بتفعيل وضع الإلزام (Enforce) على Firestore في Firebase App Check قبل التحقق الفعلي من التمرير في بيئة الإنتاج الحية، ولم يتم اختبار التطبيق ضد وضع Enforce بعد**.
2. **محدد الطلبات في الذاكرة (In-Memory Rate Limiter)**: حدود طلبات الذكاء الاصطناعي (`20` طلب / 10 دقائق و`200` طلب / يوم لكل مستخدم `uid`) وحدود SMTP مخزّنة حاليًا في ذاكرة عملية Express (`express-rate-limit`). عند تشغيل أكثر من نسخة (instance) على Cloud Run، لا تتشارك النسخ نفس العداد؛ للبيئات متعددة النسخ يُنصح بربط مخزن مشترك مثل Redis/Memorystore.
3. **حدود قراءات قواعد Firestore**: تعتمد `firestore.rules` على قراءة مستند `users/{uid}` للتحقق من الدور والمحافظات (لعدم استخدام Admin SDK IAM على باقة Starter Tier). يسمح Firestore بحد أقصى 10 عمليات `get/exists` لطلب المستند الواحد و20 للدفعة/المعاملة (مع احتساب كل مسار مستند فريد مرة واحدة فقط داخل الدفعة).
4. **الربط المركزي (`POST /api/central/sync`)**: معطّل افتراضيًا (`centralApiUrl` فارغ) ولا يُرسل أي بيانات أو يسجّل حالة `synced` إلا عند ضبط رابط `https://` حقيقي واستلام استجابة HTTP `2xx` فعلية، مع حماية SSRF على مستوى تحليل الرابط وعلى مستوى وقت الاتصال الفعلي عبر `undici` لمنع هجمات DNS Rebinding.
5. **حماية التنظيف لمرة واحدة (`passwordHash`)**: بعد نشر القواعد المشددة التي تمنع `passwordHash`، يجب على مدير النظام الضغط فورًا على زر **«تنظيف حقل passwordHash القديم»** من شاشة **الإدارة والتدقيق** لإزالة أي حقول موروثة من مستندات `users` القديمة، وإلا سيفشل أي تحديث لتلك الوثائق.
